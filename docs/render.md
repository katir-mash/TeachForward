# Deploy TeachForward as one Node service on Render

This guide describes the production setup; the repository has not been deployed by these instructions. Creating or enabling hosting resources is a separate owner action. No payment integration is part of TeachForward.

Keep the existing architecture: one Node.js/Express service serves both the Vite production build and `/api` on the same HTTPS origin. Do not create a Render Static Site for the full app, and do not deploy only `dist/`.

## Before creating a service

The current access and usage stores require a persistent writable disk. A normal local JSON file on a host's temporary filesystem is **not durable storage**. Render's default filesystem is ephemeral, and its persistent disks are available only for paid services. Render Free does not satisfy this deployment's durable-storage requirement. Review and approve any hosting charges yourself before creating resources; this guide does not authorize a purchase. [Render persistent disks](https://render.com/docs/disks).

The app supports **one service instance and one Node process**. Do not enable horizontal autoscaling or start multiple workers against the JSON files. Keep the disk, the stable signing secret, and private backups available across redeploys.

## Service settings

Once the owner has chosen and authorized the hosting resources, create a **Web Service** from the TeachForward repository. Use these settings:

| Render field | Value |
| --- | --- |
| Language | Node |
| Branch | The reviewed production branch |
| Root Directory | Leave blank: use the repository root containing `package.json` |
| Build Command | `npm ci --include=dev && npm run build` |
| Start Command | `npm start` |
| Health Check Path | `/api/health` |
| Instances | `1` |

Render runs Linux, so these hosted commands use `npm`. In local Windows PowerShell use `npm.cmd`. The server reads the host's `PORT` and listens for incoming requests; do not hardcode the local development port in Render. [Render web services and port binding](https://render.com/docs/web-services).

## Persistent disk

For a native Node service with Root Directory left blank, mount the disk at:

```text
/opt/render/project/src/server/data
```

This is a child directory of Render's documented native source path. Only files under the mount survive redeploys. The disk is available at runtime, not during the build or pre-deploy command. Do not move the source, build output or secret configuration onto the data mount. [Render mount paths and disk limitations](https://render.com/docs/disks#mount-path).

Both runtime JSON files must live on that disk: `access.json` for manual access and abuse controls, and `usage.json` for durable AI allowance and provider-attempt reservations. Do not publish either file to GitHub. Paths outside the TeachForward project are rejected by the stores.

## Server environment and secrets

Set runtime values in Render's **Environment** settings, not in React code, `public/`, `VITE_*` variables or a committed configuration file. Keep local `.env` and `server/admin-access.txt` private. Use the administrator password hash created by local setup; the plaintext administrator password does not belong in the hosted environment.

Use the following settings for the single native Node service. Replace the origin with its actual Render URL; do not copy the illustrative hostname literally.

| Variable | Production value |
| --- | --- |
| `NODE_ENV` | `production` |
| `APP_ORIGIN` | The exact public origin, for example `https://your-service.onrender.com`; no credentials, path, query or fragment |
| `SESSION_SECRET` | A private stable random secret of at least 32 characters; retain the same value across deploys |
| `ADMIN_PASSWORD_HASH` | The private scrypt hash generated by local `npm.cmd run setup:admin` |
| `DATA_DIRECTORY` | `/opt/render/project/src/server/data` |
| `PERSISTENT_STORAGE_CONFIRMED` | `1`, only after confirming the actual persistent disk is attached at that path |
| `OPENAI_API_KEY` | Set privately to enable Mentor; omit for an honest AI-unavailable deployment |
| `OPENAI_MODEL` | `gpt-6-luna`, or another Responses model verified for the configured key |
| `OPENAI_MAX_RETRIES` | `1` normally; `0` for a deliberately single-attempt authorized live check |
| `AI_DAILY_REQUEST_LIMIT` | `100` by default: service-wide daily provider-attempt slots |
| `AI_IP_DAILY_REQUEST_LIMIT` | `30` by default: daily provider-attempt slots per network |

`PORT` is supplied by Render. The app binds `0.0.0.0`; do not force the local port 3001. `ACCESS_DATA_FILE` and `USAGE_DATA_FILE` are optional: their defaults are `access.json` and `usage.json` inside `DATA_DIRECTORY`. Overrides must also be inside that directory. Paths outside the project or outside the declared data directory are rejected for public production.

The storage acknowledgement is an operator confirmation, **not a disk-attachment command or proof of durability**. Render and other public HTTPS production runs reject missing origin, short/missing signing secret, missing data directory or missing acknowledgement. Run the build before starting so the frontend assets are available. Local production previews still require an explicit loopback origin and signing secret; they do not require pretending a local disk is a hosted persistent disk.

The public app does not read a developer's local `server/.env` after deployment. Save and deploy changes before expecting the running process to use them; Render's **Save only** option postpones activation until the next deploy. [Render environment variables](https://render.com/docs/configure-environment-variables).

The repository's `.node-version` pins the tested **26.13.1**, and `package.json` bounds supported versions to `>=22.12 <27`. Leave Render's `NODE_VERSION` unset to use the repository pin; an existing `NODE_VERSION` overrides it. Do not set an unbounded latest version. [Render Node.js versions](https://render.com/docs/node-version).

## IP limits behind the host proxy

Network quotas need the real client address, not one shared proxy address. Render documents Cloudflare and load-balancer forwarding through `x-forwarded-for`. Configure `TRUST_PROXY=1` only if the verified path has exactly one trusted hop at the application boundary; the app does not trust arbitrary forwarded headers by default. If the actual chain differs, adapt the trusted-proxy configuration before relying on per-network limits. Verify that separate test clients are not all grouped into one proxy bucket and that forged forwarded headers do not bypass limits. Do not expose a trusted-proxy deployment directly. The persisted service-wide attempt cap remains independent of IP buckets. [Render client-IP guidance](https://render.com/articles/how-render-handles-ddos-attacks#reading-the-true-client-ip).

## Durable quota behavior

Every provider-bound Mentor request saves a reservation **before** contacting OpenAI: one browser question plus `1 + OPENAI_MAX_RETRIES` possible attempt slots for both the network and service. With one retry allowed, one question reserves two slots even if the first attempt succeeds. The browser allowance is up to 3 questions per UTC day for Free or 20 for Plus, subject to remaining network/service slots.

Only the browser question is refunded after a recorded failure; network and global attempt slots are never refunded on failures, unused retries or restarts. A crash after reservation conservatively leaves it counted. The usage store retains at most two UTC days of quota state. Raising limits or deleting/resetting the ledger is an operator change, not normal error recovery. These limits bound possible request attempts; they do not promise a particular dollar bill.

New browser identities also use persisted rolling admission limits and inactive-record retention:

| Optional setting | Default |
| --- | --- |
| `ACCESS_ID_IP_BURST_LIMIT` | `5` new identities per network per 10 minutes |
| `ACCESS_ID_IP_DAILY_LIMIT` | `40` per network per rolling 24 hours |
| `ACCESS_ID_GLOBAL_HOURLY_LIMIT` | `100` service-wide per hour |
| `ACCESS_ID_GLOBAL_DAILY_LIMIT` | `1000` service-wide per rolling 24 hours |
| `ACCESS_ID_IDLE_DAYS` | `30` days since the later of last seen or recorded manual expiry |
| `ACCESS_ID_MAX_RECORDS` | `10000`, also the hard maximum |

Active manual grants are protected from inactive-record cleanup. At capacity, the service rejects new identities rather than evicting existing active grants. These controls limit cookie-reset abuse; they are not visitor registration or a cross-device identity system.

## After deployment

1. Open the HTTPS origin and verify that the landing page, questionnaire and roadmap load together with `/api/health`.
2. Check a task, refresh, and confirm that browser progress remains intact. An API health response reports configuration; it does not call OpenAI.
3. Open `/admin`, sign in privately, and test a manual Plus grant and revocation for a test browser's Access ID. Test the public demo setting separately.
4. Redeploy once during a controlled check and verify that durable access records and daily counters remain on the disk. Administrator login and recent chat are intentionally temporary, so sign in again as needed.
5. Only when the owner authorizes provider usage, send one short Mentor question and confirm its real answer in the interface. Automated tests use offline transport and do not establish live provider access.

These checks establish this particular deployment's observed behavior. They do not guarantee continuing provider availability or certification outcomes.

## Backups and recovery

Back up both JSON stores consistently while the service is stopped or using the host's supported snapshot procedure, and retain the stable `SESSION_SECRET` in private secret storage. Restoring only access grants without usage reservations can weaken daily provider limits. Do not reset the usage file or signing secret to clear a quota or administrator login problem.

If a data file is unreadable or a write fails, preserve the file and investigate or restore a valid backup. Do not replace it with an empty JSON file to make the app start. Changing the signing secret invalidates the link to existing anonymous browser identities. Restore data and secret configuration before restarting, then repeat non-billable health and administrator checks.
